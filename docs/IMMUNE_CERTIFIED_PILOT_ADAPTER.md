# Certified pilot adapter — isolated software prototype

Updated: 2026-09-30 UTC. **Not deployed; no corpus training has started.**

The small [adapter](/vepfs-mlp2/c20250601/251105016/project/dllm_test/scripts/architecture_prototypes/certified_pilot.py) connects the existing data gate, fixed validation selection, measured model profile, provenance, and token-counted Trainer. It adds no submission command, certificate writer, checkpoint deletion, or training loop. The frozen 39-file model/runner release is unchanged. The parent thread maintains the matching root project status documents.

## Gate and construction order

`preflight(PilotRequest(...))` first calls the unchanged `assert_ready` from [immune_pretrain_v3.py](/vepfs-mlp2/c20250601/251105016/project/dllm_test/examples/llada/immune_pretrain_v3.py). Both existing dataset and downstream-scope certificates remain mandatory. Profile reads, validation selection reads, GPU inspection, model construction, and output creation follow this gate. A successful preflight only returns in-memory objects and provenance.

The current [expanded candidate](/vepfs-mlp2/c20250601/251105016/project/dllm_test/data/prepared/immune_v7_expanded_candidate_20260930/dataset_manifest.json) has no passing certificates. An actual, unmocked gate call rejects it for missing `audit_certificate.json`; the [rejection evidence](/vepfs-mlp2/c20250601/251105016/project/dllm_test/output/immune_data_readiness_20260930/certified_pilot_actual_rejection.json) records that no downstream profile/selection/model/GPU function ran and no output directory was created. This adapter does not remove any annotation or audit prerequisite and is not data certification.

`build_trainer(...)` performs that same preflight, then requires the runtime GPU name to match the measured profile and constructs the registered R20–R27 model, datasets, training arguments, and `TokenValidationTrainer`. It never calls `train`, `evaluate`, or `save`. Trainer construction may initialize an output directory only after all preflight gates succeed. The output must be a fresh path outside prepared data and must not overwrite a resume checkpoint.

## Exact evidence and validation population

Preflight verifies the existing production profile with the strict CPU JSON/SHA verifier. It binds the complete model release hash map, profile COMPLETE and summary bytes, measured microbatch, GPU, and production `ImmuneConfig(A4)` configuration. Existing profile evidence describes the model/training graph; the separate new evaluation adapter has not received a GPU release or profile.

The [selection verifier](/vepfs-mlp2/c20250601/251105016/project/dllm_test/scripts/architecture_prototypes/validation_selection.py) regenerates the fixed seed-42, at-most-256-record-per-source selection and checks its manifest, validation shards, row hashes, positions, and content digest. The adapter saves its exact source-local indices and constructs `Subset` instances directly from them, without resampling. Selection, manifest, both certificates, metric implementation, adapter dependencies, model source release, and software versions are bound in provenance.

The adapter references `validation_metrics.METRIC_PROTOCOL` dynamically and hashes the [metric implementation](/vepfs-mlp2/c20250601/251105016/project/dllm_test/scripts/architecture_prototypes/validation_metrics.py); it owns no copied metric-field list. The accepted protocol is `immune.token_validation.v2.aa_end_relation_and_full_mask_first_terminal`. Metric changes therefore invalidate old adapter provenance. AA, END, and explicitly supervised binding/nonbinding-prefix tokens have separate counts and loss components, whose sums preserve total selected-token CE. Token/source weighting and four-mask means remain distinct, and absent metric populations remain undefined. First-END metrics use full-mask target slots including capacity tails; their reference labels are used for scoring, not for the model feature interface. END accuracy at true END positions is recall, so it must be read with false positives/precision and first-END/length measures.

Small validation sources are reported, not expanded by moving records or splitting families. In the current candidate, native and TRAIT each retain four validation records/families. Its fixed selection contains 1,288 records overall. These counts do not establish adequate statistical power or downstream generalization.

## Training and resume contract

The adapter preserves the registered production backbone, variant options, training `model.forward` objective, natural source sampling, seed/data seed 42, global batch 256, and FP32 parameters/Adam state with BF16 autocast. The measured microbatch must divide 256. AdamW is explicitly `adamw_torch`, matching the existing worker's default and avoiding a newer local Transformers default changing the optimizer silently.

Training arguments preserve the 10,000-step cosine horizon, learning rate `1e-4`, 100 warmup steps, and evaluation/save every 100 steps. `PilotStop` controls an initial stop at 1,000 or a continuation to **cumulative** 5,000; the horizon never resets to the stage length. Single-process execution, `disable_tqdm=True`, and `dataloader_persistent_workers=False` are required by the prototype evaluation implementation.

Resume validation reuses the old complete-state/provenance check and additionally checks the model config, vocabulary, refined architecture schema/options, saved global step, and checkpoint directory name. A 5,000-step request must start from completed step 1,000, or resume an interrupted 5,000-stage checkpoint. An interrupted first stage may continue toward 1,000. All provenance except the declared stop step must match, including exact validation indices, data/certificate bytes, profile, model and adapter source hashes, metric protocol, batch/schedule, and software versions. Existing legacy or synthetic checkpoints do not acquire compatibility merely by renaming their directories.

Full optimizer/scheduler/RNG state remains required. `save_only_model=False` and the old `save_total_limit=3` are preserved. The existing pool cleanup separately protects the latest two checkpoints, an actually tracked best checkpoint, and pending/running resume references. The adapter does not delete anything and does not configure or promise a best checkpoint.

## CPU validation and remaining integration

[Tests](/vepfs-mlp2/c20250601/251105016/project/dllm_test/scripts/tests/immune_llada/test_certified_pilot.py) use temporary invented prepared rows and explicit interface mocks. Mock certificate documents say `not_a_certificate`, contain no passing status, and are never used as real gate evidence. Mock checkpoint files are placeholders for metadata-contract tests, not trained or numerically resumable weights. The real missing/pending-certificate rejection tests do not mock `assert_ready`.

Final combined acceptance passed in both environments: **48 adapter + 28 token-validation + 14 endpoint tests = 90 tests per environment**. Local Python 3.10.19 / Transformers 4.57.6 passed in 8.60 seconds; worker Python 3.12.12 / Transformers 4.48.1 passed in 10.90 seconds. Coverage includes gate ordering, no side effects on rejection, exact subsets, Trainer wiring without execution, malformed or stale evidence, interrupted/cumulative-stage provenance, missing checkpoint state, and real `TrainingArguments` CPU construction. Additional real factory tests exercise the R20/R27 registered bridge with tiny dimensions, redirect only the device move to CPU, and verify variant options, whole-layer checkpointing, seed-42 RNG reset, and the actual natural sampler. An independent read-only review found no remaining blocking issue.

The [combined acceptance JSON](/vepfs-mlp2/c20250601/251105016/project/dllm_test/output/immune_token_validation_v2_20260930/final_acceptance.json) records the metric implementation and both metric-test hashes, adapter/test hashes, both environments, log/JUnit paths and hashes, actual candidate rejection, and cleanup. Separate [adapter evidence](/vepfs-mlp2/c20250601/251105016/project/dllm_test/output/immune_data_readiness_20260930/certified_pilot_validation.json) binds that report. All 39 model-release source hashes still match all eight existing R20–R27 profiles. Five owned temporary test directories, totaling 2,322,199 bytes, were removed; no test checkpoint remains there. Only existing autocast deprecation warnings occurred. No CPU mock proves data readiness, model learning, or numerical equality of real resumed training.

Before any future real pilot, a separate release must incorporate this adapter and the finalized metric protocol, address the remaining dataset certification prerequisites, and explicitly validate the resulting GPU execution/evaluation path. The existing [enqueue helper](/vepfs-mlp2/c20250601/251105016/project/dllm_test/scripts/enqueue_immune_refined.py) owns the completed 25/500-step diagnostic promotion requirements; this adapter does not duplicate those checks and is not a complete training admission system. The future runner must preserve that admission path, persist provenance/execution requests, pass the verified checkpoint to `trainer.train(resume_from_checkpoint=...)`, retain the existing initial/final evaluation and completion checks, and recheck source stability. Those lifecycle operations remain outside this prototype; no frozen runner file has been changed here.
